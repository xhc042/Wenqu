# 问渠 v1.1 — 速读模式 vs 细读模式 代码对比分析

## 一、整体架构定位

| 维度 | 速读模式 (`speed`) | 细读模式 (`standard`) |
|------|-------------------|----------------------|
| 核心策略 | **知识快照 + 精华提炼** | **逐章掌握项 + 均匀采样** |
| 认知深度 | `basic` | `standard` |
| 推荐时长 | 15 分钟 | 30 分钟 |
| 最小轮次 | 3 | 6 |
| 掌握项策略 | 只提取全书最重要 20%（5-15 条） | 逐章生成 1-3 条（全覆盖） |

---

## 二、处理流程对比

### 速读模式流程

```
用户上传 → 文本提取 → TOC-First 分章
  ↓
【速读专属】内容采样：首段300字 + 尾段300字（_sample_first_last）
  ↓
【速读专属】逐章生成知识快照（extract_chapter_snapshot）
  ├─ keywords（关键词）
  ├─ core_viewpoint（核心观点）
  ├─ learning_goal（学习目标）
  ├─ importance（重要性 1-5）
  └─ difficulty（难度）
  ↓
【速读专属】全局精华提炼（generate_global_highlights）
  ├─ 跨章核心知识点
  ├─ 章节依赖关系
  └─ 推荐学习顺序
  ↓
【速读专属】精华掌握项生成（generate_speed_read_syllabus）
  └─ 从全书精选 20% 核心知识点（5-15 条）
  ↓
对话学习（深度=basic，最小轮次=3）
```

### 细读模式流程

```
用户上传 → 文本提取 → TOC-First 分章
  ↓
【细读专属】均匀采样（sample_chapter_fairly，5000字）
  └─ 按比例分配每段采样字符数，保证全书代表性
  ↓
逐章保存（前3章 full 加载，后续 lazy load）
  ↓
【细读专属】教学大纲生成（generate_syllabus_items）
  └─ 每章 1-3 条掌握项（全覆盖）
  ↓
对话学习（深度=standard，最小轮次=6）
```

### 关键差异点

| 环节 | 速读 | 细读 |
|------|------|------|
| 章节内容存储 | 仅存 500 字符（首尾采样） | 存 5000 字符（均匀采样） |
| 章节 full 加载 | 全部 lazy（is_loaded=0） | 前 3 章 full，其余 lazy |
| LLM 调用次数 | 每章 1 次快照 + 1 次全局精华 + 1 次掌握项 | 每章 1 次掌握项 |
| 掌握项来源 | 全局精选 5-15 条 | 逐章生成，数量 = 章节数 × 1~3 |
| 知识快照 | **有**（每章） | **无** |
| 全局精华 | **有**（跨章分析） | **无** |

## 三、内容采样规则差异

### 速读模式 — `_sample_first_last()`

```python
# chunker.py L641-651
def _sample_first_last(text: str, max_per_sample: int = 300) -> str:
    """取文本的首段和尾段作为预览"""
    paragraphs = [p.strip() for p in text.split('\n\n') if p.strip()]
    first = paragraphs[0][:max_per_sample]
    last = paragraphs[-1][:max_per_sample]
    return f"{first}\n\n...（中间内容略）...\n\n{last}"
```

**特点**：
- 只取首段 + 尾段，每段最多 300 字
- 中间内容直接省略
- 目的是快速让 LLM 理解章节大意，节省 Token

### 细读模式 — `sample_chapter_fairly()`

```python
# chunker.py L1146-1172
def sample_chapter_fairly(text: str, target_chars: int = 5000) -> str:
    """按章节均匀采样，保证全书代表性"""
    ratio = target_chars / total_chars
    for para in paragraphs:
        sampled_chars = min(len(para), int(len(para) * ratio) + 500)
        sampled.append(para[:sampled_chars])
```

**特点**：
- 按比例从**每一段**采样
- 目标 5000 字符，保证全书代表性
- 不是简单截取前 N 字

## 五、代码合理性分析

### 优点

1. **分层清晰**：速读模式通过"快照 → 全局精华 → 精华掌握项"三级 LLM 调用，实现了从局部到全局的知识提炼，架构设计合理。

2. **Token 优化**：速读模式采用首尾采样（300+300字），大幅减少输入 Token，适合快速扫描大量章节的场景。

3. **容错机制完善**：
   - 快照生成有 3 次重试 + 文本兜底（_extract_keywords_fallback）
   - 全局精华有 _build_highlights_fallback 兜底
   - 元数据章节（序言/前言）被正确识别并降低重要性

4. **细读均匀采样**：`sample_chapter_fairly` 按比例分配采样，避免了"只取前 N 字"的偏差问题。

5. **LLM 分级调度**：配置中定义了 fast/balanced/flagship 三层模型，速读和细读使用 balanced，研读使用 flagship，成本与效果平衡合理。

### 问题与优化建议

#### 1. 速读模式的 LLM 调用开销过大

**问题**：速读模式虽然意图是"快速"，但实际 LLM 调用次数可能比细读更多：
- 每章 1 次快照调用
- 1 次全局精华调用
- 1 次精华掌握项调用
- 总计 = 章节数 + 2 次

而细读模式每章只需 1 次掌握项调用。

**建议**：
- 考虑对章节数 > 15 的书籍，快照生成使用批量处理（一次性传入多章内容）
- 或引入缓存机制：相同书籍重复导入时复用快照

#### 2. `generate_speed_read_syllabus` 的 `target_count` 计算过于粗糙

**代码位置**：[chunker.py L1256-1257](file:///d:/Tiger/Wenqu%20v1.1/chunker.py#L1256-L1257)

```python
total_estimated = len(chapters) * 3
target_count = max(5, min(15, int(total_estimated * 0.2)))
```

**问题**：假设 50 章 × 3 = 150，150 × 0.2 = 30，被 min(15) 截断为 15。这意味着无论多少章，最多只保留 15 条掌握项，可能丢失重要信息。

**建议**：
- 改用 `global_highlights` 中的 `key_points` 作为掌握项来源，避免重复 LLM 调用
- 或根据章节重要性加权计算 target_count

#### 3. 速读/细读的章节内容存储不一致

**问题**：[app.py L239-244](file:///d:/Tiger/Wenqu%20v1.1/app.py#L239-L244)

速读模式存 500 字符，细读存 5000 字符。但速读的 `content` 已经是首尾采样后的结果（最多 ~600 字），所以 `content[:500]` 几乎保留了全部采样内容。这个设计本身合理，但注释不够清晰。

#### 4. `_probe` 状态的 temperature 偏高

**代码位置**：[state_machine.py L215](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L215)

```python
async for chunk in llm.chat_stream(self.messages, temperature=0.7):
```

PROBE 状态（提问）使用 temperature=0.7，可能导致问题质量不稳定。评估（_eval）使用 0.3，讲解（_explain）使用 0.5，但提问也用了 0.7。

**建议**：PROBE 状态温度降至 0.5，使提问更加稳定可控。

#### 5. 辩论触发条件过于简单

**代码位置**：[state_machine.py L527-536](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L527-L536)

```python
agreement_keywords = ["是的", "对", "有道理", "没错", "你说得对", "确实", "同意", "明白了"]
agreement_count = sum(1 for kw in agreement_keywords if kw in user_text)
return agreement_count >= 2 and self.current_round > 2
```

**问题**：
- 关键词匹配容易被误触发（例如用户说"对，我有不同看法"）
- 没有考虑上下文语义

**建议**：使用 LLM 判断用户是否"完全认同"，或用更复杂的启发式规则。

#### 6. 课后闭环并行执行中，思辨笔记无条件调用

**代码位置**：[state_machine.py L665](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L665)

```python
self._generate_spiritual_notes() if self.depth == "deep" else noop(),
```

**问题**：思辨笔记只在 `depth == "deep"` 时生成，但"研读"模式对应的是 `reading_mode == "deep"`，而 `depth` 字段在会话创建时可能被设置为 "basic"/"standard"/"deep"。两者不一定对齐。

**建议**：确认 `reading_mode` 和 `depth` 的对齐逻辑，或在 `_generate_spiritual_notes` 中也检查 `reading_mode`。

#### 7. 心流检测逻辑可改进

**代码位置**：[state_machine.py L394-402](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L394-L402)

```python
if len(user_text) > FLOW_DETECTION["reply_length_threshold"] and \
   ("?" in user_text or "为什么" in user_text or "如何" in user_text or "是不是" in user_text):
```

**问题**：
- 只检查单条消息是否包含问号，忽略了用户可能在连续回答中展现深度思考
- 阈值 50 字符可能偏低

**建议**：结合最近 N 条消息的平均长度和问题密度综合判断。

## 六、总结

| 维度 | 速读 | 细读 |
|------|------|------|
| 适用场景 | 快速浏览、复习、时间紧张 | 系统学习、备考 |
| LLM 成本 | 高（快照+精华+掌握项） | 中（仅掌握项） |
| 知识覆盖率 | 低（20% 精华） | 高（全覆盖） |
| 对话深度 | 浅（basic，3轮起步） | 中（standard，6轮起步） |
| 内容呈现 | 首尾采样，省 Token | 均匀采样，保代表性 |
| 产出物 | 知识快照 + 全局精华 + 精华掌握项 | 掌握项 + 复习总结 |

**核心设计哲学**：速读模式是**"先提炼再学习"**——先用 LLM 做知识蒸馏，对话时只围绕精华展开；细读模式是**"边学边掌握"**——逐章推进，通过对话逐步掌握每个知识点。

## 一、问题诊断

**用户反馈**：
> "我学完一轮后，感觉没有学到主要知识。"
> "学习章节的时候，问了几轮问题后，总是在最基础的知识讨论，还没到主要知识，这节课就结束了。"

**根因分析（reading-mentor 视角）**：

3 层独立缺陷叠加形成因果链：

| 层级 | 缺陷 | 影响 |
|---|---|---|
| L1 精华生成 | prompt 要求"能+动作"通用格式 | LLM 倾向生成"放之四海皆准"的泛化模板 |
| L2 章节分配 | round-robin 分配后无重要性标记 | 对话阶段不知道哪个是核心 |
| L3 对话学习 | 状态机 PROBE/SHARE 无差别取前 3 条 | LLM 默认挑容易的基础概念先问 |

### L1/L2/L3 定位

| 层级 | 现状 | v1.3 目标 |
|---|---|---|
| L1 读完 | ✅ 章节快照存了 | 保持 |
| L2 读懂 | ⚠️ 泛化 key_points | ✅ **本书独有的核心观点** |
| L3 会用 | ❌ 对话跑偏 | ✅ **对话必触核心 + 防白上保险** |

## 三、方案与落地

### 3.1 P0：三层一起改（根本集合）

#### 任务 1 — 数据库层（db-migrator 视角）

**改动**：`syllabus_items` 表加 `importance` 字段(1-5,5=最核心)
- `CREATE TABLE IF NOT EXISTS` 加字段
- `_migrate_schema()` 检查字段后 ALTER TABLE 向后兼容
- `add_syllabus_item(course_id, ch_idx, desc, importance=3)` 默认 3 向后兼容
- `get_syllabus_items` 排序改为 `ORDER BY chapter_index, importance DESC, id`

**收益**：核心知识在查询结果中永远排在前面

#### 任务 2 — 精华生成层

**改动**：`chunker.generate_global_highlights` prompt 强化"本书独有"原则
- 旧 prompt 要"能+具体动作"通用格式 → LLM 倾向泛化
- 新 prompt 要求每条 key_point 必须：
  - 引用快照中的具体关键词/观点/方法
  - 能区分"这本书"与"其他讲类似主题的书"
  - 离开这本书就不成立
- 提供 ✅ 好例子（锚定具体书）和 ❌ 坏例子（禁止泛化）

**收益**：key_points 从"通用能力描述"变成"本书独特洞见"

#### 任务 3 — 分配层

**改动**：`_run_speed_mode_postprocess` 按 key_points 排序生成 importance 梯度
- 前 30% → importance=5
- 中间 40% → importance=4
- 后 30% → importance=3
- `_persist_speed_results` 兼容旧 tuple 格式 `(ch_idx, desc, importance)`

**收益**：核心 key_points 自动打 5 分，写入 DB

#### 任务 4 — 状态机 SHARE 阶段

**改动**：`_get_mastery_hint` 按 importance desc 取，文本标记 `[重要度N/5]`

**收益**：SHARE 阶段 LLM 优先讲核心观点

#### 任务 5 — 状态机 PROBE 阶段

**改动**：`_get_mastery_check` 按 importance desc 取，prompt 加约束
- 必须先围绕 `[重要度4-5]` 提问
- 不要停留在基础概念定义
- 优先问"应用/对比/判断"类问题

**收益**：PROBE 阶段 LLM 优先问核心

#### 任务 6 — 状态机 SHARE prompt

**改动**：SHARE prompt 加核心优先约束
- 必须先揭示本章最核心的观点
- 用具体例子/案例/数据支撑核心观点

**收益**：用户进入 SHARE 就听到核心，不被基础定义浪费时间

### 3.2 P1-任务 7：核心触达保险（防白上）

**改动**：`handle_user_input` 结束判断分支加核心触达保险
- `_has_touched_core()`: 检查本章是否触达过 importance≥4 syllabus
- `_force_core_probe()`: 未触达则构造强制 PROBE prompt
- `_core_probe_attempted` 标记：每章节最多触发 1 次强制 probe，防死循环

**边界场景**：

| 场景 | 行为 |
|---|---|
| A 已触达核心 | 正常结束 |
| B 未触达 + 未尝试 | 强制 PROBE 一次后判断 |
| C 未触达 + 已尝试 | 正常结束（防死循环） |
| D 进心流 | 不结束，正常 PROBE |
| E 未到 min_rounds | 不结束，正常 PROBE |

**收益**：即使 LLM 跑偏，15min/3轮 结束时系统强制追加 1 轮核心 PROBE，**保证用户学完不白上**

## 四、关键发现

### 4.1 三层缺陷必须一起改

> 单独改任何一层都不够。模糊的精华 → 模糊的分配 → 模糊的对话，因果链完整。

### 4.2 schema 迁移 + 默认值是兼容性的关键

- 旧库启动自动 `ALTER TABLE` 加字段
- 新代码默认 `importance=3`（中等），向后兼容
- 老 syllabus_items 重新生成课程可拿真实梯度

### 4.3 防死循环的"一次性尝试"模式

P1-任务 7 用 `_core_probe_attempted` 标记 + 强制 probe 后再次判断 `_has_touched_core()` 实现"只追加一次"的保险。避免"为了保证学完核心而无限延长课时"的反模式。

### 4.4 post-commit hook 自动化

每次 commit 后自动跑 `pytest -m 'not slow'` + 5 项 code-reviewer checklist（并发安全 / LLM 兜底 / 资源管理 / 边界条件 / 状态机违规）。本次 commit `f5c52ec` 触发后 hook 全过，验证机制有效。

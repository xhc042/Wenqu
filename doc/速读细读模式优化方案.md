## 优化1：速读模式 LLM 调用开销优化

### 问题分析

**现状**：速读模式虽然意图是"快速"，但实际 LLM 调用次数可能比细读更多：
- 每章 1 次快照调用（`extract_chapter_snapshot`）
- 1 次全局精华调用（`generate_global_highlights`）
- 1 次精华掌握项调用（`generate_speed_read_syllabus`）
- 总计 = **章节数 + 2 次**

而细读模式每章只需 1 次掌握项调用。对于一本 50 章的书，速读模式需要 52 次 LLM 调用，细读模式约 50 次。两者调用次数相当，但速读模式的调用质量要求更高（temperature=0.3），且需要更复杂的 prompt。

**核心矛盾**：速读模式的"快"体现在对话阶段（3轮起步），而非预处理阶段。

### 优化方案

#### 方案 A：快照批量处理（推荐）

将逐章快照改为批量处理，一次 LLM 调用处理多章内容。

```python
# chunker.py - 新增批量快照函数
async def extract_batch_snapshots(chapters: list, batch_size: int = 10) -> list:
    """
    批量提取章节快照，减少 LLM 调用次数
    
    Args:
        chapters: [(title, content, meta), ...]
        batch_size: 每批处理的章节数，默认10
    
    Returns:
        [snapshot_dict, ...]
    """
    all_snapshots = []
    
    for i in range(0, len(chapters), batch_size):
        batch = chapters[i:i + batch_size]
        
        # 构建批量 prompt
        batch_entries = []
        for idx, (title, content, meta) in enumerate(batch):
            chapter_num = i + idx + 1
            is_meta = is_non_core_chapter(title)
            text_sample = content[:1500] if not is_meta else content[:800]
            
            batch_entries.append(
                f"--- 第{chapter_num}章 {title} ---\n"
                f"{'[元数据]' if is_meta else '[正文]'}\n"
                f"{text_sample}"
            )
        
        prompt = f"""你是读书导师。请为以下{len(batch)}个章节分别提炼知识快照。

{chr(10).join(batch_entries)}

请返回JSON数组，每个元素对应一个章节：
[
  {{
    "chapter_index": 0,
    "keywords": ["关键词1", "关键词2"],
    "core_viewpoint": "一句话核心观点",
    "learning_goal": "能+具体动作",
    "importance": 3,
    "difficulty": "中等"
  }},
  ...
]

注意：
1. 每个章节独立分析，不要混淆
2. 元数据章节（序言/前言等）importance 强制 1-2
3. importance 评分基于章节在整个书中的价值（1-5）"""

        try:
            result = await llm.chat_json([
                {"role": "system", "content": "你是知识提炼专家。严格返回JSON数组。"},
                {"role": "user", "content": prompt},
            ], temperature=0.3)
            
            batch_snapshots = result if isinstance(result, list) else []
            all_snapshots.extend(batch_snapshots)
        except Exception as e:
            # 批次失败时降级为逐章处理
            for title, content, meta in batch:
                snapshot = await extract_chapter_snapshot(content, title)
                all_snapshots.append(snapshot)
    
    return all_snapshots
```

**预期收益**：
- LLM 调用次数从 `N` 次降至 `ceil(N/10)` 次（N=章节数）
- 50 章书籍：52 次 → 7 次（减少 86%）
- 单次调用时间增加约 3-5 秒，但总耗时大幅降低
- Token 利用率提高（系统提示词只需发送一次）

#### 方案 B：快照缓存机制

对相同书籍的重复导入，复用已有快照数据。

```python
# chunker.py - 新增快照缓存
import hashlib
from datetime import datetime, timedelta

def _compute_content_hash(text: str, title: str) -> str:
    """计算章节内容哈希，用于缓存命中判断"""
    # 只取前500字计算哈希，减少计算开销
    return hashlib.md5(f"{title}:{text[:500]}".encode('utf-8')).hexdigest()

async def get_cached_snapshot(course_id: str, chapter_idx: int) -> Optional[dict]:
    """
    检查是否有可用的缓存快照
    
    缓存策略：
    - 相同 book_hash（全书内容指纹）
    - 相同 chapter_index
    - 缓存时间 < 30天
    """
    conn = db.get_conn()
    try:
        row = conn.execute("""
            SELECT s.*, c.book_hash, c.created_at
            FROM chapter_snapshots s
            JOIN courses c ON s.course_id = c.id
            WHERE s.chapter_index = ?
            AND c.reading_mode = 'speed'
        """, (chapter_idx,)).fetchone()
        
        if row:
            # 检查缓存时效
            created = datetime.fromisoformat(row['created_at'].replace('Z', '+00:00'))
            if datetime.now() - created < timedelta(days=30):
                return {
                    "keywords": json.loads(row['keywords']) if row['keywords'] else [],
                    "core_viewpoint": row['core_viewpoint'],
                    "learning_goal": row['learning_goal'],
                    "importance": row['importance'],
                    "difficulty": row['difficulty'],
                    "cached": True,
                }
    finally:
        conn.close()
    return None

async def generate_course_book_hash(text: str) -> str:
    """计算全书内容指纹，用于缓存匹配"""
    # 取每章前200字拼接后计算哈希
    sample_parts = []
    for para in text.split('\n\n')[:50]:  # 最多取前50段
        sample_parts.append(para[:200])
    sample = '\n'.join(sample_parts)
    return hashlib.sha256(sample.encode('utf-8')).hexdigest()
```

**预期收益**：
- 重复导入相同书籍时，快照生成时间从分钟级降至秒级
- 数据库存储增加约 5-10KB/课程（可忽略）
- 缓存命中率预估 30-50%（用户可能反复导入热门书籍）

## 优化2：`generate_speed_read_syllabus` 掌握项生成优化

### 问题分析

**现状代码** ([chunker.py L1256-1257](file:///d:/Tiger/Wenqu%20v1.1/chunker.py#L1256-L1257)):

```python
total_estimated = len(chapters) * 3
target_count = max(5, min(15, int(total_estimated * 0.2)))
```

**问题**：
1. `min(15)` 硬性截断导致 50 章以上书籍最多只保留 15 条掌握项
2. 与 `generate_global_highlights` 中的 `key_points`（5-10条）功能重复
3. 额外消耗 1 次 LLM 调用

### 优化方案

直接使用 `global_highlights.key_points` 作为掌握项来源，消除重复调用。

```python
# chunker.py - 优化后的速读掌握项生成
async def generate_speed_read_syllabus_from_highlights(
    course_id: str, 
    snapshots: list, 
    highlights: dict
) -> list:
    """
    从全局精华中提取精华掌握项，避免重复 LLM 调用
    
    Args:
        highlights: generate_global_highlights 返回的结果
            包含 key_points, chapter_priorities, core_chapter_indices
    
    Returns:
        [(chapter_index, description), ...]
    """
    key_points = highlights.get("key_points", [])
    core_indices = highlights.get("core_chapter_indices", [])
    
    if not key_points:
        return []
    
    # 策略1：直接使用 key_points 作为掌握项
    # key_points 格式已经是"能+具体动作"
    syllabus_items = []
    for i, point in enumerate(key_points[:10]):  # 最多10条
        # 尝试从 point 文本中推断所属章节
        # 如果 key_points 不包含章节信息，按重要性分配
        if i < len(core_indices):
            # 核心章节的掌握项
            ch_idx = _parse_chapter_num(core_indices[i])
            if ch_idx >= 0:
                syllabus_items.append((ch_idx, point))
        else:
            # 非核心章节的掌握项，分配到重要性最高的章节
            syllabus_items.append((0, point))
    
    # 策略2：如果 key_points 不足 5 条，补充全局关键词
    if len(syllabus_items) < 5:
        for snapshot in sorted(snapshots, key=lambda s: s.get("importance", 3), reverse=True)[:5]:
            if len(syllabus_items) >= 10:
                break
            ch_idx = snapshot.get("chapter_index", 0)
            keywords = snapshot.get("keywords", [])
            if keywords:
                syllabus_items.append((
                    ch_idx,
                    f"能描述{keywords[0]}的核心要点"
                ))
    
    return syllabus_items[:15]  # 最多15条


def _parse_chapter_num(s: str) -> int:
    """从"第N章"格式提取章节索引"""
    import re
    m = re.search(r'第(\d+)章', str(s))
    return int(m.group(1)) - 1 if m else -1
```

**修改 app.py 中的调用**：

```python
# app.py - 在 generate_global_highlights 之后直接复用
highlights = await generate_global_highlights(course_id, snapshots, chapter_titles)
db.add_global_highlights(...)

# 优化后：不再调用 generate_speed_read_syllabus
syllabus_items = await generate_speed_read_syllabus_from_highlights(
    course_id, snapshots, highlights
)
```

### 预期收益

| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| LLM 调用次数 | 3 次（快照×N + 全局精华 + 掌握项） | 2 次（快照×N + 全局精华） | -33% |
| 掌握项数量 | 5-15 条（截断） | 5-10 条（key_points）+ 补充 | 更精准 |
| 生成时间 | 章节数 × 2s + 5s + 3s | 章节数 × 2s + 5s | -3s |
| 数据一致性 | key_points 与掌握项可能不一致 | 同源数据，完全一致 | 提升 |

## 优化4：PROBE 状态 temperature 调优

### 问题分析

**现状代码** ([state_machine.py L215](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L215)):

```python
async for chunk in llm.chat_stream(self.messages, temperature=0.7):
```

**问题**：
- PROBE 状态（提问）使用 temperature=0.7，问题质量波动大
- 同文件中 EVAL 使用 0.3，EXPLAIN 使用 0.5，GUIDE 使用 0.5
- 提问应该是"有创见的但不过于发散"，0.7 偏高

### 优化方案

```python
# state_machine.py - 修改 PROBE 温度

async def _probe(self) -> AsyncGenerator[str, None]:
    """PROBE状态：AI提出1个问题"""
    self.state = self.PROBE
    
    # ... 构建 messages ...
    
    # 优化：temperature 从 0.7 降至 0.5
    # 理由：提问需要一定的创造性，但更要保证质量和相关性
    # 0.5 是创造性和稳定性的平衡点
    content_parts = []
    async for chunk in llm.chat_stream(self.messages, temperature=0.5):
        content_parts.append(chunk)
        yield chunk
    
    # ...
```

**各状态 temperature 对照表**：

| 状态 | 用途 | 当前 temp | 建议 temp | 理由 |
|------|------|-----------|-----------|------|
| SHARE | 复述教材 | 0.7 | 0.5 | 复述应忠实原文 |
| PROBE | 提出问题 | 0.7 | **0.5** | 提问需有深度但不过于发散 |
| EVAL | 评估回答 | 0.3 | 0.3 | 评估需客观准确 |
| EXPLAIN | 讲解知识点 | 0.5 | 0.5 | 讲解需清晰易懂 |
| GUIDE | 拉回主题 | 0.5 | 0.5 | 引导需自然 |
| DEBATE | 辩论 | 0.9 | 0.9 | 辩论需要强烈观点 |

### 预期收益

| 指标 | 优化前 | 优化后 | 改善 |
|------|--------|--------|------|
| 问题质量稳定性 | 低（波动大） | 高 | 显著提升 |
| 问题相关性 | 中 | 高 | +15-20% |
| Token 消耗 | 无变化 | 无变化 | - |
| 实施成本 | - | 1行代码 | 极低 |

## 优化5：辩论触发条件优化

### 问题分析

**现状代码** ([state_machine.py L527-536](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L527-L536)):

```python
async def _check_debate_trigger(self, user_text: str) -> bool:
    agreement_keywords = ["是的", "对", "有道理", "没错", "你说得对", "确实", "同意", "明白了"]
    agreement_count = sum(1 for kw in agreement_keywords if kw in user_text)

```

**问题**：
1. 关键词匹配容易被误触发（"对，但我认为..."会被判定为完全认同）
2. 没有考虑上下文语义
3. 用户可能只是礼貌性回应，并非真正认同

### 优化方案

```python
# state_machine.py - 优化辩论触发逻辑

async def _check_debate_trigger(self, user_text: str) -> bool:
    """
    检测是否触发反方辩论
    
    触发条件（需同时满足）：
    1. 用户轮次 >= 3（已建立基本对话）
    2. 用户近2次回答都表现出高度认同
    3. 当前回答中认同信号较强
    """
    if self.current_round < 3:
        return False
    
    # 策略1：关键词分析（快速过滤）
    agreement_positive = ["是的", "对", "有道理", "没错", "你说得对", "确实", "同意", "明白了", "有道理"]
    agreement_negative = ["不对", "不是", "不同意", "恰恰相反", "恰恰相反", "我认为不对"]
    
    pos_count = sum(1 for kw in agreement_positive if kw in user_text)
    neg_count = sum(1 for kw in agreement_negative if kw in user_text)
    
    # 如果有否定词，直接排除
    if neg_count > 0:
        return False
    
    # 至少2个正面认同词才进入下一步判断
    if pos_count < 2:
        return False
    
    # 策略2：检查最近2条用户消息的一致性
    messages = db.get_messages(self.session_id)
    user_messages = [m for m in messages if m["role"] == "user"][-4:]  # 最近4条消息
    
    if len(user_messages) < 2:
        return False
    
    # 检查最近2条用户消息是否都有认同倾向
    recent_agreement = 0
    for msg in user_messages[-2:]:
        content = msg.get("content", "")
        # 简单的语义判断：消息长度适中 + 无疑问词
        if 20 < len(content) < 200 and "?" not in content and "？" not in content:
            # 检查是否有认同表达
            for kw in agreement_positive:
                if kw in content:
                    recent_agreement += 1
                    break
    
    # 策略3：使用轻量 LLM 判断（可选，精度最高）
    if recent_agreement >= 1:
        # 确认用户确实表现出连续认同
        try:
            judgment = await llm.chat_json([
                {"role": "system", "content": "你是对话分析助手。判断用户是否完全认同教师观点。"},
                {"role": "user", "content": f"""
最近对话：
教师：{messages[-4].get('content', '')[:200] if len(messages) > 3 else ''}
学生：{messages[-3].get('content', '')[:200] if len(messages) > 2 else ''}
教师：{messages[-2].get('content', '')[:200]}
学生：{messages[-1].get('content', '')[:200]}

请判断学生是否连续两次完全认同教师的观点。
如果是，返回：{{"should_debate": true, "reason": "原因"}}
如果不是，返回：{{"should_debate": false, "reason": "原因"}}
"""}
            ], temperature=0.3)
            return judgment.get("should_debate", False)
        except Exception:
            # LLM 判断失败时回退到关键词规则
            return recent_agreement >= 1
    
    return False
```

| 真触发率 | 中 | 高 | +15% |

## 优化7：心流检测逻辑改进

### 问题分析

**现状代码** ([state_machine.py L394-402](file:///d:/Tiger/Wenqu%20v1.1/state_machine.py#L394-L402)):

```python
def _check_flow_state(self, user_text: str):
    """心流检测"""
    if self.current_round >= FLOW_DETECTION["min_rounds"]:
        if len(user_text) > FLOW_DETECTION["reply_length_threshold"] and \
           ("?" in user_text or "为什么" in user_text or "如何" in user_text or "是不是" in user_text):
            self.is_flow_state = True
            self.flow_extend_count += FLOW_DETECTION["auto_extend_rounds"]
        else:
            self.is_flow_state = False
```

**问题**：
1. 只检查单条消息是否包含问号，忽略了用户可能在连续回答中展现深度思考
2. 阈值 50 字符可能偏低（用户回复"这个问题我想到三个方面"就算深度？）
3. `else` 分支将心流状态直接设为 False，可能导致刚进入心流就被退出
4. 没有考虑用户的追问质量（是深入追问还是跑题？）

### 优化方案

```python
# state_machine.py - 优化心流检测

def _check_flow_state(self, user_text: str):
    """
    心流检测：综合多维度判断用户是否进入深度学习状态
    
    心流入场条件（满足至少2项）：
    1. 回复长度 > 100 字符
    2. 包含追问信号（疑问词、深入探讨意愿）
    3. 连续2次回复长度 > 50 字符
    4. 提及前文内容（显示理解了之前的讨论）
    
    心流出场条件（满足任意1项）：
    1. 连续3次回复 < 20 字符
    2. 明确表示不想继续
    """
    if self.current_round < FLOW_DETECTION["min_rounds"]:
        return
    
    flow_signals = 0
    total_checks = 4
    
    # 信号1：回复长度
    if len(user_text) > 100:
        flow_signals += 1
    elif len(user_text) > 50:
        flow_signals += 0.5  # 中等长度算部分信号
    
    # 信号2：追问信号
    question_signals = ["为什么", "如何", "是不是", "怎样", "因为", "所以", "但是", "如果"]
    has_question_signal = any(sig in user_text for sig in question_signals)
    has_question_mark = "?" in user_text or "？" in user_text
    
    if has_question_signal and has_question_mark:
        flow_signals += 1
    elif has_question_signal or has_question_mark:
        flow_signals += 0.5
    
    # 信号3：连续深度回复
    messages = db.get_messages(self.session_id)
    user_msgs = [m for m in messages if m["role"] == "user"][-3:]  # 最近3条
    
    avg_length = sum(len(m.get("content", "")) for m in user_msgs) / max(len(user_msgs), 1)
    if avg_length > 50:
        flow_signals += 1
    
    # 信号4：提及前文（简单启发式：包含代词或前文关键词）
    previous_assistant = [m for m in messages if m["role"] == "assistant"]
    if previous_assistant:
        last_assistant_content = previous_assistant[-1].get("content", "")
        # 检查是否引用了前文内容
        if any(keyword in user_text for keyword in last_assistant_content[:50].split()):
            flow_signals += 1
    
    # 判断是否进入心流
    if flow_signals >= 2:  # 满足至少2项信号
        self.is_flow_state = True
        self.flow_extend_count += FLOW_DETECTION["auto_extend_rounds"]
    elif not self.is_flow_state:
        # 只在未进入心流时才重置，避免频繁切换
        pass
    else:
        # 已处于心流状态：连续3次低信号才退出
        low_signal_count = sum(1 for m in user_msgs[-3:] if len(m.get("content", "")) < 20)
        if low_signal_count >= 3:
            self.is_flow_state = False


# config.py - 调整检测参数
FLOW_DETECTION = {
    "min_rounds": 3,
    "reply_length_threshold": 50,  # 保留作为向后兼容
    "auto_extend_rounds": 3,
    "probe_timeout_seconds": 120,
    "flow_signal_threshold": 2,     # 新增：进入心流需要的信号数
    "exit_low_signal_count": 3,     # 新增：连续低信号次数才退出心流
}
```
